# JM 轻量版 v1.2.4 升级日志

**版本号**：versionName 1.2.4 / versionCode 19
**日期**：2026-10-02
**DB**：沿用 v13（无 schema 变更）
**包名**：`com.example.jmreader`

## 版本说明

修复用户反馈的「**一口气下载多个，下载管理里却没有**」。

---

## 一、根因：写库发生在「排队拿到名额」之后

`DownloadManager` 有一条**书本级并发闸门**（刻意设计，非 bug）：

```kotlin
/** 固定 2 本同时下载。不能做成配置项——下载就该温和排队… */
private val bookDownloadSemaphore = Semaphore(2)
```

而**写数据库记录的时机在闸门之后**：

```kotlin
suspend fun downloadAlbum(albumId: Int) {
    bookDownloadSemaphore.acquire()          // ← 先排队拿名额
    try {
        downloadAlbumInternal(albumId)       // ← 记录写在这里面
    } finally { release() }
}

private suspend fun downloadAlbumInternal(albumId: Int) {
    downloadDao.upsert(Download(bookId = albumId, status = "DOWNLOADING", …))   // ← 这里
```

**后果**：一口气下载 10 本时，只有**排在最前的 2 本**能拿到名额并写下记录，
**其余 8 本全部挂在 `acquire()` 上干等，数据库里没有任何痕迹** ——
而「下载管理」的数据源就是 `downloads` 表，因此**这 8 本完全不可见**。

> 从用户视角看就是"点了下载，下载管理里什么都没有"；但实际上它们只是在安静排队。

---

## 二、修复

### ① 入队即落记录（`downloadAlbum`）

在 `acquire()` **之前**先写一条 `QUEUED` 记录：

```kotlin
runCatching {
    val cur = downloadDao.get(albumId)
    if (cur == null || cur.status == "DONE" || cur.status == "FAILED") {
        downloadDao.upsert(Download(bookId = albumId, status = "QUEUED", createdAt = now))
    }
}
bookDownloadSemaphore.acquire()
…
```

| 已有记录状态 | 处理 |
|---|---|
| 无记录 | 写入 `QUEUED` |
| `DONE` / `FAILED`（重新下载） | 覆盖为 `QUEUED`，重置进度 |
| `DOWNLOADING` / `QUEUED`（已在队列） | **跳过**，不覆盖 |

**UI 无需改动** —— `DownloadsScreen` 早已支持该状态：
`"QUEUED" -> "排队中…"`；进入实际下载后由 `downloadAlbumInternal` 覆盖为 `DOWNLOADING`。

### ② 启动恢复纳入 QUEUED（`resumePendingDownloads`）

该逻辑原本只恢复 `status == "DOWNLOADING"` 的任务。本次修复开始产生 `QUEUED` 记录，
若进程在排队期间被杀，这些记录**永远不会被重新入队**，会一直卡在"排队中…"：

```kotlin
.filter { it.status == "DOWNLOADING" || it.status == "QUEUED" }
```

## 四、需要说明：并发 2 是刻意设计，不是缺陷

排队本身**符合预期**（源码注释明确：书本级并发固定 2，避免 12×12 请求触发源站风控）。
本次修复**没有放宽并发**，只是让排队中的任务**在界面上可见**（显示"排队中…"），
从而消除"点了没反应"的错觉。

若希望同时下载更多本，需要新增一个可配置项并评估风控风险 —— 属产品决策，未擅自改动。
