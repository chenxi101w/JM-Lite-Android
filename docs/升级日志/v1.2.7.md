## 一、【真问题】通知权限：申请了但根本没用

### 排查结论

| 检查 | 结果 |
|---|---|
| Manifest 是否声明 `POST_NOTIFICATIONS` | ✅ 声明了（第 9 行） |
| 首次启动是否主动请求 | ✅ 请求了（`MainActivity` 用 `rememberLauncherForActivityResult` 拉起） |
| **全工程是否有通知实现** | ❌ **零** —— 搜不到任何 `NotificationCompat` / `NotificationManager` / `createNotificationChannel` |

**结论：这是一个纯粹的冗余权限** —— 每次冷启动都弹一次「是否允许通知」，
但 App 压根没有任何通知功能。用户会疑惑「一个漫画阅读器为什么要通知权限」，属无谓的打扰与信任损耗。

### 修复

1. `AndroidManifest.xml`：移除 `<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />`；
2. `MainActivity.kt`：移除启动时的权限请求代码块（`notifLauncher` 及其 `LaunchedEffect` 分支），
   保留同一 `LaunchedEffect` 内的配置迁移逻辑（那是无关的另一件事）。

> 如日后要做「下载完成通知」，再把权限与通知渠道一起加回来即可 —— 注释里已写明。

## 二、【构建优化】release 终于开启 R8

### 根因：release 和 debug 一样臃肿

```kotlin
release {
    isMinifyEnabled = false      // ← 代码不裁剪、不混淆
    proguardFiles(...)
}
```

**release 关着 R8**，等于出的是「未优化的包」。实测 debug APK 42.4MB，解压后构成：

| 内容 | 解压后 |
|---|---|
| `classes.dex` | **42.23 MB** |
| `classes17.dex` | 13.07 MB |
| `assets/chaquopy` | 12.81 MB |
| `lib/arm64-v8a` | 10.30 MB |
| 合计 | 83.7 MB（压缩后 42.4MB） |

> 注：`abiFilters` **早已只保留 `arm64-v8a`** —— 这项无需再优化。

### 改动

**`app/build.gradle.kts`**：

```kotlin
release {
    isMinifyEnabled = true        // 开 R8 代码裁剪/混淆
    isShrinkResources = true      // 顺带压缩无用资源（需配合上面才生效）
    proguardFiles(...)
    signingConfig = signingConfigs.getByName("debug")   // 测试用，便于 CLI 装机验证
}

lint {
    // AGP + Kotlin 当前组合下 lintVitalAnalyzeRelease 自身会崩
    // （findFirCompiledSymbol only works on compiled declarations），与业务无关
    checkReleaseBuilds = false
}
```

**`app/proguard-rules.pro`** 补充规则：应用自身数据层/模型整体保留、
Kotlin 元数据属性保留、OkHttp/Okio/Coil 告警抑制、协程规则。

原有规则（Chaquopy、Room）已在文件中保留。

### ⚠️ 尚未验证 —— 需在 Android Studio 里打包

CLI 构建 release **必须失败**，原因是 Chaquopy 的 pip 环境依赖：

```
Execution failed for task ':app:installReleasePythonRequirements'
> Process 'command '...\build\python\env\release\Scripts\python.exe'' finished with non-zero exit value 1
```

跳过该任务后，`mergeReleaseAssets` 又因 Chaquopy 的资产任务依赖断裂而失败
（`... before task ':app:generateReleasePythonRequirementsAssets' has completed is not supported`）。

这与项目既有认知一致：**Chaquopy 工程完整包只能在 AS 构建**。

**预期收益**：R8 通常可减小 **30%~50%** dex 体积，预计 release 包落到 **20~25MB** 量级。
**风险**：R8 若与 Chaquopy/反射有未覆盖的冲突，可能引发运行时崩溃 ——
**必须先装机完整测试**（下载、搜索、阅读三条链路）。

## 三、【确认正常】用户数据 24.9 MB

实测设备 `dataDir` 构成（`du` 输出，KB）：

| 路径 | 大小 | 性质 |
|---|---|---|
| `files/chaquopy` | **13.8 MB** | Chaquopy 首次运行解压的 Python 运行时（bootstrap 1.6M + stdlib 2.8M + requirements 4M 等）——**使用 Python 的必要开销** |
| `cache/coil_disk` | **11.9 MB** | Coil 封面磁盘缓存（**已设 256MB 上限**，远未触及） |
| `databases` | 596 KB | Room 数据库 |
| `no_backup` | 168 KB | |
| `shared_prefs` | 12 KB | |
| 合计 | **≈ 26.4 MB** | 与关于页显示的 24.9MB 吻合 |

> 关于页的「安装包大小」= `applicationInfo.sourceDir` 文件长度（即 APK 本身）；
> 「用户数据占用」= `dataDir` 递归求和。两个数字的算法都是准确的。

**可选优化（未实施，待用户决定）**：
- 把 Coil 磁盘上限从 256MB 降到 64MB（封面图不需要那么大）；
- 在设置页加「清除封面缓存」入口。
> Chaquopy 的 13.8MB 无法避免，除非放弃 Python 链路（会失去 author/tags 搜索等能力）。
