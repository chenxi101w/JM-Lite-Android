## 一、UI：失败 / 排队中也能续下（关键）

### 问题

「重新下载」按钮的判断是：

```kotlin
if (dl.status == "DONE") {          // ← 只对已完成显示
    IconButton(onClick = onRedownload) { Icon(Icons.Filled.Refresh, …) }
}
```

**下载一旦 `FAILED`，卡片上除了「取消并删除」再无其他操作** ——
用户只能删掉重来，而已下载的部分白白浪费（虽然 Python 侧其实能续传）。

### 修复

```kotlin
if (dl.status == "DONE" || dl.status == "FAILED" || dl.status == "QUEUED") { … }
```

状态文案也从 `"失败（可取消并删除）"` 改为
**`"失败 · 点右侧 ⟳ 继续下载（已下部分会保留）"`** —— 明确告诉用户"还能续"。

## 二、自动重试：上限 2 → 4，并加退避

```kotlin
private val MAX_AUTO_RETRY = 4          // 原为硬编码 2
…
delay(minOf(5_000L shl tries, 30_000L)) // 原为固定 5_000
```

| 第几次重试 | 等待 |
|---|---|
| 1 | 5s |
| 2 | 10s |
| 3 | 20s |
| 4 | 30s（封顶） |

**为什么加退避**：原来固定 5 秒，网络刚断时连续快速重试基本是白试，还可能加重源站风控。

超限后才标 `FAILED`，而 `FAILED` 现在可以一键续下（见上文），不会丢进度。

## 三、排队记录卡住 → 自动重新入队（新增）

### 问题

任务写下了 `QUEUED` 记录，但对应的协程异常退出（或旧版本遗留）后，
**没有任何人会再处理它** —— 界面上永远停在「排队中…」。原 watchdog 只认 `DOWNLOADING`。

### 修复

在 watchdog 中新增一段：

```kotlin
val anyActive = all.any { it.status == "DOWNLOADING" }
if (!anyActive) {
    for (dl in all) {
        if (dl.status != "QUEUED") continue
        if (now - dl.createdAt <= QUEUE_STUCK_MS) continue   // 60s：给它排队的耐心
        if (autoRetrying.contains(dl.bookId)) continue
        …重新入队…
    }
}
```

**判据必须带 `!anyActive`** —— 否则正常排队（前面还有书在下、这本只是排得靠后）
会被误判成卡死而反复重新入队。

## 四、卡死判据的两个漏洞

原判据：

```kotlin
if (p.status != "DOWNLOADING" || p.mtime <= 0) continue   // 直接放过
if (now - p.mtime <= STUCK_THRESHOLD_MS) continue
```

两个问题：

| 情况 | 原行为 | 现行为 |
|---|---|---|
| **进度文件读不到**（`mtime<=0`，如刚开下就卡死、连进度文件都没写出来） | 直接跳过 → **永远不会被处理** | 退回用记录 `createdAt` 兜底判断 |
| **进度文件显示已完成**（Python 完成了但落库没跟上，如进程被杀） | 直接跳过 → **永远停在「下载中」** | 直接 `reconcileDownloadStatus(bookId, "DONE")` 纠正 |
