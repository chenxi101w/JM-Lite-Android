## 一、体验：书架长按删除（新增）

### 背景

书架的 `ComicCard` **早就支持** `onLongClick` 与 `onDelete`，但 `LibraryScreen` 调用
`ComicGrid` 时**没有传 `onBookLongClick`** —— 所以长按毫无反应；
卡片上的删除按钮也只对**已下载**的书显示，且**点一下直接删、没有二次确认**。

### 改动

| 项 | 原 | 现 |
|---|---|---|
| 长按卡片 | 无反应 | 弹出删除确认 |
| 卡片「已下载 → 删除」按钮 | **直接删除，无确认** | 同样走确认弹窗 |
| 确认文案 | — | 按是否已下载区分：<br>有本地文件 → 「将删除已下载的本地文件，并清除书架记录与阅读进度」<br>无本地文件 → 「将从书架移除…并清除阅读进度」 |
| 提示 | — | 删除后 Toast「已删除」 |

删除语义未变：`vm.removeBook(id)` → `repo.removeBookCompletely(id)`（**彻底删除，不可恢复**）。

## 二、体验：压缩封面与标题之间的留白

### 根因

封面与标题之间夹着一条 `ComicActionBar`（左：下载/删除，右：收藏）。它的实现里：

```kotlin
// 左侧无内容时 —— 塞一个 32dp 占位
} else { Spacer(Modifier.size(32.dp)) }
```

而书架上**绝大多数书未下载**（无下载/删除按钮），且 `LibraryScreen` **未接收藏回调** ——
于是这条操作条**两侧都空**，却仍占约 **40dp**（32dp 占位 + 上下各 4dp padding），
白白夹在封面与标题中间。这就是看到的留白。

### 改动（`ComicCard.kt` · `ComicActionBar`）

1. **整条在没有任何可显示操作时直接不渲染**（`if (!showLeft && !showRight) return`）——
   未下载的书省下整条 40dp；
2. 上下 padding `4dp → 1dp`，有按钮时也更紧凑；
3. 顺带修正：右侧收藏原先**漏了 `!selectionMode` 判断**，多选态下会与左侧不一致，现统一。

## 三、性能：列表 contentType + 搜索短时缓存

### ① contentType（共 9 处）

给各类列表补上 `contentType`，让**不同类型的 item 不再互相复用**（Compose 复用只应发生在同类型之间）：

| 位置 | contentType |
|---|---|
| 详情页章节列表 / 相关推荐 | `"chapter"` / `"related"` |
| 阅读器页面（两处：滚动 / 览） | `"page"` |
| 书架卡片（网格 / 未看完 / 已看完） | `"book"` |
| 下载列表 | `"download"` |
| 首页更新列表 | `"update"` |

### ② 搜索结果短时缓存（`SearchViewModel`）

**场景**：从详情页 / 阅读页返回搜索页，或短时间内重复搜同一条件。

**实现**：60 秒 TTL 的内存缓存（上限 8 条，超出淘汰最旧），
键 = `mode|keyword|page|orderBy|time|tagsLogic|tagsJson`（任一条件不同即不命中）。
命中时直接复用上次的 raw + 可见列表 + hasMore，**跳过网络（keyword）或 Python（author/tags）链路**。

**已知取舍**：命中时不重跑过滤，因此 60 秒内改动「隐藏已下载 / 已看完」等设置不会即时反映 ——
窗口很短，换来的是返回搜索页零等待。

## 四、性能：加速切换下一章

### 先纠正一个前提

原计划是「预取下一章的页列表」。但 `loadChapter` 的注释与实现表明：
**自 v5.0.18 起在线阅读已移除，只有已下载章节能读**，切章 = 扫描本地目录（几十毫秒）。
因此**预取路径列表几乎没有收益**。

### 实际改动：改为预热图片

真正会「顿一下」的是切过去之后**首屏图片的解码**。因此：

1. `ReaderViewModel.peekNextChapterPaths(bookId, chapterId, limit)`（新增）——
   在 IO 线程只读地取下一章**前 N 张**图片路径，**不修改任何阅读状态**；
2. `ReaderScreen` 在滚动接近本章末尾（`firstVisibleItemIndex >= totalPages - 2`）时，
   把这 3 张提前 enqueue 进 Coil 内存缓存，**每章只预热一次**。

效果：切到下一章后首屏可直接命中缓存，无需等待解码。

## 五、性能：Baseline Profile

新增 `app/src/main/baseline-prof.txt`，覆盖冷启动热点：

| 范围 | 内容 |
|---|---|
| 应用自身 | `com/example/jmreader/**` |
| Compose | `runtime` / `ui.platform` / `ui.node` / `ui.layout` / `foundation` / `material3` / `animation` |
| 框架 | `activity` / `lifecycle` / `navigation` |
| 数据层 | `room`（启动即开库读书架） |
| 其他 | `kotlinx.coroutines`、`coil`（首屏封面） |

### ⚠️ 两条必须知道的限制

1. **debug 包不含 profile**。实测 debug APK 内只有
   `META-INF/androidx.profileinstaller_profileinstaller.version`，**没有 `assets/dexopt/baseline.prof`** ——
   这是 AGP 的标准行为：**baseline profile 只在 release 构建打包**。所以「装个 debug 包试试快了没」是测不出来的。
2. **这是手写版，非真机轨迹**。最精准的做法是 Macrobenchmark 的 `BaselineProfileRule`
   （需额外建 benchmark 模块 + 真机执行）。当前版本零依赖、随构建生效，收益通常低于真机生成的版本。

### 附带发现（与本次改动无关）

构建 release 时 `lintVitalAnalyzeRelease` 崩溃：

```
Unexpected failure during lint analysis (this is a bug in lint or one of the libraries it depends on)
Message: `findFirCompiledSymbol` only works on compiled declarations...
```

这是 **Android Lint 自身在分析 Kotlin 脚本（build.gradle.kts）时的 bug**，与业务代码无关。
临时绕过：`./gradlew assembleRelease -x lintVitalAnalyzeRelease`。
若长期需要出 release 包，可在 `app/build.gradle.kts` 里配置 `lint { checkReleaseBuilds = false }`。
