## 一、核心修复：纯数字搜索（JM 号）每次都掉回 Python

### 现象

用户反馈「搜索速度不对劲」。真机实测日志：

```
W JmRepository: JSON 接口搜索无结果，回退 Python 链路
界面显示：上次搜索 1540 ms · Python链路
```

而换英文关键词搜索是 `395 ms · JSON接口` —— 说明接口链路本身是好的。

### 根因

接口对**纯数字查询**的语义不同：不返回列表，而是给出「跳转目标」：

```json
{"search_query":"350234", "search_type":"site", "total":1,
 "redirect_aid": 350234, "content": []}
```

原实现只读 `content`，看到空数组就判定「接口无结果」→ 回退 Python。
**接口其实已经给出了答案（`redirect_aid`），我们却白白多花 1.1 秒。**

### 修复（`JmApiClient.search`）

```kotlin
// 识别跳转语义：拿 redirect_aid 再取一次 album 详情，返回单条结果
val redirectAid = json.optInt("redirect_aid", 0)
if (redirectAid > 0) return listOfNotNull(albumBrief(redirectAid))
```

新增 `albumBrief(aid)`：调 `album` 接口取标题/作者/标签/页数。
注意 album 的 `author` 与 `tags` 都是**数组**，需拼接（实测多作者会返回 7 个元素）。

### 效果（真机实测，同一 JM 号连搜三次）

| 次数 | 出发链路 | 耗时 |
|---|---|---|
| 第 1 次 | JSON接口 | 1934 ms |
| 第 2 次 | JSON接口 | 1913 ms |
| **第 3 次** | JSON接口 | **755 ms** |

- 修复前：`Python链路 1540 ms`（每次都走 Python）
- 修复后：`JSON接口`，**稳定态 755 ms，约为 Python 的一半**
- 前两次偏慢是**服务端缓存未命中**（首次请求触发服务端缓存该书详情），非客户端问题

## 二、封面源优化（v1.1.4）

### 背景

搜索本身很快（接口 283~597ms 返回 80 条），但**封面加载才是体感瓶颈**：

| 源 | 单张均值 |
|---|---|
| `cdn-msp.jmapiproxy1.cc` + `_3x4` | **133 ms** ✅ 采用 |
| `cdn-msp3 / cdn-msp2.jmapiproxy1.cc` + `_3x4` | 137 / 142 ms |
| `www.cdnhjk.net` + 原图（原实现） | 227 ms |

原实现是**跟随 API 线路**拼封面（`https://<api-host>/media/albums/<id>.jpg`），
而 API 那几条线路（cdnhjk / cdngwc）做封面反而更慢。

### 修复

封面改用**独立的最快封面源**，与 API 线路解耦；并改用 `_3x4` 缩略图后缀（更小更快）。
新增 `COVER_HOSTS` 列表（按速度排序，保留备用便于切换）。**单张 227ms → 133ms，快 41%。**

## 三、线路配置预热（v1.1.4）

线路配置原本只在**首次搜索时**才拉取（实测 **924 ms**），拖慢冷启动后的第一次搜索。
现在在 `JmComicApplication.onCreate` 里后台预热，之后搜索直接用内存缓存。

## 六、遗留观察

- JM 号搜索需 **2 次串行请求**（search 拿 redirect_aid → album 拿详情），
  稳定态 755ms。若要进一步压到 ~400ms，可考虑只用 `redirect_aid` 构造结果
  （代价：标题临时显示为 `JM-<id>`），当前未采用 —— 书名正确更重要。
- 前两次搜索慢（~1.9s）是服务端缓存冷启动，客户端无法规避。
