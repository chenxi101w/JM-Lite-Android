## 一、致命问题：进阅读器崩溃

### 现象

```
java.lang.IllegalStateException: Size is unspecified
    at androidx.compose.ui.geometry.Size.getWidth-impl(Size.kt:49)
    at ...ReaderScreenKt.ReaderScreen$lambda$...(ReaderScreen.kt:412)
```

### 根因

v1.1.2 为了消除留白，改成按图片真实宽高比布局：

```kotlin
val sz = painter.intrinsicSize
if (sz.width > 0f && sz.height > 0f && !sz.width.isNaN() && !sz.height.isNaN()) ...   // ❌
```

**Compose 的 `Size.Unspecified` 是哨兵值（内部为 NaN 编码），读取它的 `.width` / `.height`
会直接抛 `IllegalStateException`** —— 也就是说 `> 0f`、`isNaN()` 这些「兜底判断」在取值那一步就已经炸了，
根本没有机会生效。图片尚未加载完成时 `intrinsicSize` 正是 `Size.Unspecified`，于是必然崩溃。

### 修复

```kotlin
// 必须先判 isSpecified，再取值
val ratio = if (sz.isSpecified && sz.width > 0f && sz.height > 0f)
    sz.width / sz.height
else DEFAULT_PAGE_RATIO
```

（`androidx.compose.ui.geometry.isSpecified`）

## 二、连带发现：主线程磁盘 IO（掉帧真凶）

同一份日志里 StrictMode 给出了明确证据：

```
StrictMode policy violation; ~duration=11 ms: DiskReadViolation
    at java.io.UnixFileSystem.getBooleanAttributes → File.isDirectory   (ReaderViewModel.kt:247)
StrictMode policy violation; ~duration=10 ms: DiskReadViolation
    at java.io.UnixFileSystem.list                → File.listFiles      (ReaderViewModel.kt:248)
StrictMode policy violation; ~duration=10 ms: DiskReadViolation
    at java.io.UnixFileSystem.getBooleanAttributes → File.isFile       (ReaderViewModel.kt:249)
```

`loadChapter()` 运行在 `viewModelScope`（Main 调度器），而 `loadLocalPaths()` 直接扫描本地目录，
**主线程阻塞约 31ms** —— 与日志里那些 `jank frame: 33.1 ms` 完全对得上。

### 修复

| 位置 | 改动 |
|---|---|
| `ReaderViewModel.loadChapter()` | `loadLocalPaths(...)` 包进 `withContext(Dispatchers.IO)` |
| `BookLibrary.rebuildChaptersFromLocal()` | 目录扫描整体包进 `withContext(Dispatchers.IO)`（v1.1.1 新增的方法，同样会在 Main 被调用） |

## 三、v1.1.2 内容回顾（留白修复）

- **根因**：原实现 `AsyncImage(contentScale = Fit, height = 屏高 × 0.95f)` ——
  图片比例与固定框不符时，空出的部分全是留白（702×1000 的页会白空约 30% 屏高）。
- **修复**：改为按图片真实宽高比 `FillWidth` 铺满宽度；页间距 4dp → 0；去掉每页 padding；
  去掉右侧滑轨预留的 8dp；占位框用 0.72 比例避免高度跳变。
- ⚠️ 该版本的宽高比取值写法有缺陷（见第一节），已在 v1.1.3 修正。

## 五、教训（写入项目笔记）

1. **Compose 的 `Size` / `Offset` / `Dp` 等 inline class 有 Unspecified 哨兵值，读属性会抛异常**，
   必须先用 `isSpecified` 判断 —— 静态检查与编译都发现不了。
2. **UI 渲染路径的改动必须真机验证**：编译器能过 ≠ 运行不崩。CLI 编译只是最低门槛。
3. **不要把「某次日志里没有 StrictMode 输出」当成「主线程干净」的结论** ——
   不同操作路径（后台切换 vs 进入阅读器）覆盖的代码不同，需按场景分别验证。
