# v1.8.7 — 对齐官方客户端的并发量级（为什么原生版跑不过 Python 版）

> 用户反馈：「**之前用 python 能稳住 1MB/S，现在怎么维持不住了，跑一会停一会**」。
>
> 这是一条**黄金基线**：Python 版（jmcomic）能跑 1MB/s，说明**网络和 CDN 都没问题**，
> 差距一定在**我们的实现参数**上。于是直接去读 jmcomic 2.7.7 的源码做逐项对比。

## 对比结果：两处量级差 + 一处策略差

用 `pip install jmcomic` 装回官方库（`C:/Users/Administrator/.workbuddy/binaries/python/envs/default`）实测：

```python
>>> o = jmcomic.JmOption.default()
>>> o.download.threading.image
30
>>> o.download.threading.photo
16
```

| 维度 | Python（jmcomic 2.7.7） | 我们的原生（v1.8.6） | 差距 |
|---|---|---|---|
| 图片并发 | **30**（全局，**跨章节共享**） | 6（每本）× 2 本 = 12 | **2.5×** |
| 章节/书本并发 | **16** | 2 | **8×** |
| 图片域名 | **每张图 `random.choice` 6 个域名** | 固定 1 个，慢才切 | 负载全压单 CDN |
| 解码线程池 | `min(32, cpu+4)`（本机 = 20） | 6（两本共享） | — |
| HTTP 连接池 | `max_clients = image_concurrency = 30` | 16 | — |

### 域名策略的证据

`jm_toolkit.py:444`：

```python
if image_domain is None:
    import random
    image_domain = random.choice(JmModuleConfig.DOMAIN_IMAGE_LIST)
```

**每张图随机挑一个 CDN**（6 个候选）。于是 30 个并发请求天然摊到 6 个 CDN 上，
单个 CDN 的限速不会成为整体天花板。

而我们**所有并发都打同一个域名** —— 单域名限速 = 整体天花板，
这正是「跑一会停一会」的波形来源（并发被压制 + 批次效应）。

### 顺带确认：域名列表完全一致

`JmModuleConfig.DOMAIN_IMAGE_LIST` 与我们 `JmApiClient.IMAGE_DOMAINS` 的 6 个域名**逐一相同**，
只是官方在 import 时 `shuffled()` 过一次。所以不是域名选错，是**用法**错了。

| `NativeAlbumDownloader` | **域名起点改为「健康域里随机挑」**（对齐 `random.choice`），新增 `pickStartDomainIndex()` / `markDomainOk()` / `markDomainFail()`；移除 `goodDomainIndex` 与 `markDomainSlow()` |

### 为什么不直接设 30

我们是「**每本一份**并发池」的结构（官方是全局一份跨章节共享）。
16 × 2 本 = 32，与官方 30 同量级；再往上对手机内存/CPU 压力大
（每张图都要解码 + JPEG 重编码，一张 1200×1700 解码后约 8MB）。

### 域名随机化为什么不能是「纯随机」

历史上实测过 `cdn-msp.jmapiproxy1.cc` 在真机上长时间不可用
（早期日志里「域名 … 不可用，改用 …」重复 7 次）。纯随机会让每 6 张图
就有 1 张先撞一次超时。

所以加了一层**健康度记忆**：

```
域名连续失败 2 次 → 冷却 10 分钟（domainCooldownUntil）
起步时只在「未冷却」的域名里随机挑；冷却中的仍作为回退候选排在后面
```

配合 `connectTimeout` 20s → **8s**：万一随机到真不可用的域名，也能**快速失败**回退，
不再白白吃掉 20 秒。

### 为什么移除「慢域名惩罚」(`markDomainSlow`)

它与随机分散**互相冲突**：分散本身就是把负载摊到 6 个 CDN，
慢域名自然只占 1/6 份额；再叠加惩罚会破坏分散性、逼回单域名。
慢现在**只记日志**（verbose 下），不参与调度决策。

## 兼容性处理：老用户 DB 里的旧默认值

老用户 DB 已持久化 `"max_concurrent_downloads=6"`，改 `defaultConfigs` 对他们**无效**
（只有首次建库才写默认值）。而 6 已从新档位（4/8/16/24/32）中移除 ——
所以 `refreshConcurrency()` 里读到 6 就判定为「旧默认残留」，直接提到 16。

> ⚠️ 副作用：极少数**主动**选过 6 的用户会被提到 16。
> 但升级后设置页仍可手动选 4，且一般人不会特意改这项。
