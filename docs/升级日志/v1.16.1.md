# v1.16.1 — 修复下载队列「新点的下载卡住」

**版本号**：versionName 1.16.1 / versionCode 78
**日期**：2026-10-15
**DB**：无 schema 变更
**性质**：纯修 bug（PATCH）

## 问题现象

用户报告：**只有新点的下载卡住，重启 App 和「重新下载」都能正常下**。
组合症状指向调度器：重启（新进程、新 scope）与重下（force 路径）都绕过了出问题的状态。

## 根因（v2.0 队列的 5 处缺陷，全部位于 `DownloadManager.kt`）

### ① scope 无 SupervisorJob —— 一个子协程翻车，全家陪葬（最重）

`scope = CoroutineScope(Dispatchers.IO)` 的根 Job 是**普通 Job**。`runDownload` 无 catch，
而 `downloadAlbumInternal` 的 catch 块会显式 `throw e` —— 任何非取消异常逃出 `runDownload`
就会**连带取消整个 scope**：watchdog、启动恢复、之后所有 `dispatch` 的 `scope.launch`
全部变成「已取消态，body 不执行」，而 `enqueue` 还在照常往 pending/active 放死任务。
表现正是「新点的下载静默卡住」。**修复**：根 Job 改 `SupervisorJob()`，
且在 `runDownload` 内收官异常（`CancellationException` 重抛，其余落 FAILED 后腾位）。

### ② finally 的 `active.remove(albumId)` 无身份校验

`cancelDownload` / 强制重下是「先摘 entry 再 cancel」，旧任务的迟到 finally 若无条件 remove，
会把同书**新任务**的 entry 一起摘掉 → 新任务脱离监控 → watchdog 之后取消它全是空转 →
同书重复并发下载不断累积。**修复**：`active.remove(albumId, self)`（`self = coroutineContext[Job]`）。

### ③ enqueue 与 dispatch 无互斥 —— dispatch 丢弃已 poll 的任务

强制重下的 `active.remove → cancel → pending.add` 与旧任务 finally 交错时，
`dispatch` 的 `active.containsKey(id) → continue` 把已 poll 的同一本书**直接丢弃** →
书落入「QUEUED 记录但不在任何队列」的 limbo，界面永远显示「排队中（队列第 N 位）」。
**修复**：enqueue 的队列变更段与 finally 的「摘 entry + dispatch」纳入同一把 `dispatchLock`。

### ④ QUEUED 落库与 dispatch 无序 —— 幽灵排队

`scope.launch { 写 QUEUED }` 与同步启动的下载竞争：迟到的 QUEUED 写会把已经 DOWNLOADING、
甚至已 DONE 的记录**覆盖回「排队中」**。**修复**：`dispatch()` 移入同一个 launch、落库之后执行。

### ⑤ watchdog ① 的 anyActive 判据被陈旧记录永久挡住

`all.any { it.status == "DOWNLOADING" }` 把陈旧 DOWNLOADING 记录（杀进程残留 / 幽灵写入）
当成"有下载在跑"，limbo QUEUED 书的救援**永不触发**。**修复**：要求记录确实在
`active`/`pending` 队列里才算 anyActive。

### 顺带校对

注释与常量漂移对齐：停滞判据注释写 10s、watchdog 写 30s，实际 `STALL_RESET_MS = 60s`、
`WATCHDOG_INTERVAL_MS = 5s` —— 以代码为准改注释。

## 验证

- 编译：`gradlew compileDebugKotlin` BUILD SUCCESSFUL（exit 0，`:app:compileDebugKotlin` 实际执行）。
- 真机（待用户确认）：① 新点下载立即进入下载；② 弱网卡死后 watchdog 60s 判据自动续下；
  ③ 连续下多本不出现「排队中」假象。

## 备注

- `dispatch()` 现延迟一个 DB 往返启动（毫秒级），换取 QUEUED 记录保序。
- 若真机仍有残留症状，抓 logcat 定位：`adb logcat -s DownloadManager | findstr /C:"调度" /C:"入队" /C:"取消" /C:"停滞" /C:"收官"`（ PowerShell ），
  重点看有没有「调度异常：同时在 active 与 pending」与「下载任务异常收官」两条新日志。
