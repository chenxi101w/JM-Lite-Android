# JM 轻量版 v1.1.0 升级日志

**版本号**：versionName 1.1.0 / versionCode 3
**日期**：2026-09-29
**DB**：沿用 v13（无 schema 变更）
**包名**：`com.example.jmreader`

## 版本说明

本版两件事：**① 搜索提速（换数据链路）**、**② 搜索耗时记录与导出**。

起因：对比同源客户端（Capacitor + React 版 `com.JMComic3.app`）后发现其搜索明显更快。
逆向其客户端协议后确认：它走的是 JM 镜像方提供的 **JSON 接口**，而本工程走的是
`Kotlin → Chaquopy → Python 3.11 → jmcomic 2.7.3 → requests 抓 HTML → 解析 DOM`。
差距来自数据链路本身（HTML 解析 + Python 解释器 + 跨语言调用），不是 UI 实现。

本版新增 Kotlin 原生接口客户端，**保留全部现有 UI 与 Compose 架构**，只替换搜索的数据来源。

## 一、新增文件

| 文件 | 职责 |
|---|---|
| `data/api/JmApiCrypto.kt` | 协议加解密：MD5 签名、AES-256-ECB 解密（线路配置 / 接口响应） |
| `data/api/JmApiHost.kt` | 线路发现与容灾：拉取并解密线路配置、进程内缓存、失败自动切换下一条 |
| `data/api/JmApiClient.kt` | OkHttp 客户端：带签名请求 `search`，解密响应，映射为 `Book` |
| `util/SearchPerfLog.kt` | 搜索耗时日志：采样、紧凑字母串编解码、汇总统计 |

## 二、协议实现要点

- **线路配置**：从两条字节云对象存储源拉取加密 txt，`AES-256-ECB`（密钥 `md5("diosfjckwpqpdfjkvnqQjsik")`）
  解密得到 `Server` 列表（实测解出 4 条线路），顺序选一条作为 `apiUrl`。
- **请求签名**：`Token = md5(time + "185Hcomic3PAPP7R")`，头 `Tokenparam: "<time>,<version>"`。
- **响应解密**：`{code:200, data:"<base64>"}`，`AES-256-ECB` 密钥 `md5(time + "185Hcomic3PAPP7R")` → JSON。
- **封面**：接口不返回封面，按实测可用的规则构造 `https://<线路>/media/albums/<id>.jpg`。
- 单次请求失败自动换线路重试（最多 3 次）。

## 三、搜索耗时记录（同批新增）

### 采样

`JmRepository.search()` 在两条链路各自计时并写入 `SearchPerfLog`：

| 来源码 | 含义 |
|---|---|
| `A` | JSON 接口成功 |
| `P` | Python 链路 |
| `F` | 接口失败（空结果/异常），随后回退 Python |

**只记录「耗时 + 来源」，绝不记录搜索关键词、结果内容或任何用户数据。**

### 紧凑编码（便于发给电脑）

样本以字母串持久化（SharedPreferences，上限 400 条），**每样本 4 字符**：

```
[来源码 1 字符][耗时 3 字符 base36]     3 位 base36 上限 46655ms（46.6 秒）
```

整串示例：`A01fA00zP2k9` → 三次搜索（两次接口、一次 Python）。

电脑端解码（Python）：

```python
s = "A01fA00zP2k9"          # 从 App「关于」页复制的串
for i in range(0, len(s) - 3, 4):
    print(s[i], int(s[i+1:i+4], 36), "ms")
```

### 界面

- **搜索页**：搜索框下方显示「上次搜索 132 ms · JSON接口」。
- **关于页**：新增「搜索耗时记录」区块 —— 记录条数 / 平均 / 最快最慢 / 接口与 Python 各自的次数与均值 /
  接口失败回退次数，以及紧凑记录串（可长按选择），并提供 **复制**、**分享**（系统分享，可发微信/QQ/邮件）、**清空**。

## 五、启用范围（保守，可逐步放开）

当前仅在**纯关键词搜索 + 默认排序/时间 + 无标签条件**时走接口：

```kotlin
if (USE_API_SEARCH && mode == "keyword" && tagsJson.isBlank()
    && orderBy == "mr" && time == "a") { ... }
```

原因：接口的排序（`o`）、时间（`y`/`m`）、搜索类型（`search_type`）参数枚举尚未逐一验证，
这些场景继续走 Python 以保证行为一致。

**接口不可用时自动静默回退 Python 链路**，不会出现「搜不出来」的硬失败。

## 六、回退方式

- 临时整体回退：`JmRepository.USE_API_SEARCH = false`。
- 删除新增的 `data/api/` 三个文件、`util/SearchPerfLog.kt` 并还原 `search()` 即可完全恢复旧链路。

## 七、已知风险

- 接口线路为 **JM 镜像方提供的第三方服务**，域名会更换（故有线路配置源）、可能变更协议或失效。
  已做线路容灾 + Python 回退，但长期稳定性不由本工程控制。
- 接口不返回 `tags` / `pageCount`，搜索结果这两项为空（Python 链路同样存在「搜索不带标签」的问题，
  已有后台补抓标签的补偿逻辑不受影响）。
