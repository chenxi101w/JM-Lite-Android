# v1.8.4 — 修「下载速度时好时坏」（真实吞吐量，不是速度显示）

> ⚠️ **本版的部分性能调优造成了下载变慢，已在 [v1.8.5](./v1.8.5.md) 中修正。**
> 请以 v1.8.5 为准。本文件保留作为根因分析记录，其中「根因 1~4」的结论仍然成立，
> 但「根因 5（解扰限流）」与 `readTimeout` / `ConnectionPool` / `markDomainSlow` 的具体取值已被回退。

> 用户反馈：「为什么下载速度是好是坏的」，并澄清是**实际下载速度**（真实吞吐量），
> 不是界面上速度数字的抖动。
>
> 结论：**预热期被误判成卡死 → 取消 → 重下 → 再预热**的死循环，叠加另外三处吞吐瓶颈。

## 根因 1（头号）：章节清单串行拉取，预热期被停滞判据误杀

`NativeAlbumDownloader.download()` 里拉章节图片清单是一句**串行** for：

```kotlin
for (ref in chapters) {
    val detail = api.chapterDetail(ref.id) ?: continue   // 每次一次真实网络往返
    ...
}
```

而 `api.chapterDetail()` 每次都是一次 HTTP 请求；`scramble_id` 不在 `/chapter` 响应里时
还要**再**打一次 `/chapter_view_template`。30 章 = 30~60 次串行 RTT，**约 9~18 秒一张图都没在下**。

与此同时 `DownloadManager` 的停滞判据是 `STALL_RESET_MS = 10_000L`
（10 秒内字节数零增长 → 判卡死 → 取消 → 重下）。于是：

```
拉清单（十几秒，字节零增长）
  → 被判卡死 → cancelDownload()
  → 退避 delay(3s << tries)
  → downloadAlbum() 重下 → 又串行拉一遍清单
  → 再被判卡死 ……
```

完美的「一阵快一阵慢 / 好像一直在下但进度不动」。

### 修法

| 位置 | 改动 |
|---|---|
| `NativeAlbumDownloader` | 新增 `fetchChapterPlans()`：**并发**拉章节清单（`CHAPTER_FETCH_CONCURRENCY = 6`），30 章从 ~15s 降到 ~2s |
| `NativeAlbumDownloader` | 新增 `chapterDetailCache`（photoId → 详情，**TTL 10 分钟**）：watchdog 续下 / 断点续传 / 同一本重试不再重复付预热成本 |
| `DownloadManager` | `STALL_RESET_MS` 10s → **30s**（仍远快于 30s 的 readTimeout，真卡死照样兜住） |

## 根因 2：章间串行 + straggler

原来是「章内并发、章间**串行**」。每章结束都要等本章**最慢**那张图，
30 章就累计 30 次「等最慢的一张」，吞吐被反复拉回单条连接水平。

**改**：新增 `ImgJob`，把所有章的待下载页拉平成一张任务表，用一个**全局并发池**跑。
慢图只拖住它自己那一路，其余路继续吃带宽。进度语义（全局 `done`/`bytes` 原子计数）不变。

## 根因 3：OkHttp 默认每 host 只有 5 并发 / 连接池只留 5 条空闲连接

下载用的 `OkHttpClient` 之前没配 `dispatcher` 和 `connectionPool`，用默认值：

- `maxRequestsPerHost = 5` → 图片并发设 12 时，**只有 5 条真正并发**，其余在 Dispatcher 队列里排；
- `connectionPool` 默认保留 5 条空闲连接 → 超出的连接**用完即关**，下一批要重做 TCP + TLS 握手
  （每个 2~3 个 RTT）→ 吞吐**周期性塌一下再恢复**，正是「时好时坏」的波形。

**改**：显式配置

```kotlin
.dispatcher(Dispatcher().apply {
    maxRequests        = MAX_BOOK_CONCURRENCY * MAX_IMAGE_CONCURRENCY + 8
    maxRequestsPerHost = MAX_IMAGE_CONCURRENCY + 4
})
.connectionPool(ConnectionPool(MAX_IMAGE_CONCURRENCY + 4, 1, TimeUnit.MINUTES))
```

同时 `readTimeout` 60s → **30s**（单张图 1~2MB，30s 足够；真卡住时能更早回收并发位）。

## 根因 4：接口 `domain` 的兜底值架空了「上次成功域名」记忆

`JmApiClient.chapterDetail()` 里：

```kotlin
val domain = json.optString("data_original_domain").trim().ifBlank { IMAGE_DOMAINS.first() }  // ← 坑
```

`data_original_domain` 实测基本都是空的，于是 `domain` 恒为 `IMAGE_DOMAINS.first()`。
而 `fetchWithDomainFallback()` 会把「接口指定的 domain」放在候选列表**最前面** ——
`goodDomainIndex`（记住上次成功的域名）因此**永远排不上第一**，每张图都要先试一次
列表第一个域名（真机上长时间不可用/很慢）再回退。

**改**：接口没给就**留空**，交给下载器按 `goodDomainIndex` 选。

## 根因 5：解扰（解码 + JPEG 重编码）12 路全并发，打满 CPU / 内存

一张 1200×1700 的图解出约 8MB（ARGB_8888），再 JPEG 95% 重编码要几百毫秒。
12 张同时编解码 → 上百 MB 瞬时占用 + CPU 打满 → GC 抖动、网络线程被饿死。

**改**：新增 `descrambleSem`（`DESCRAMBLE_CONCURRENCY = 3`）单独限流这一步；
**网络下载仍然全并发**，不受此闸门影响。

## 其他附带修复

- 慢域名惩罚 `markDomainSlow()`：单张图取回 ≥ `SLOW_IMAGE_MS`(5s) 就把起始域名往后挪一位
  （全局冷却 15s，避免弱网下把所有域名轮一遍）。原来只记「成功」的域名，
  一旦黏上一个「慢但可用」的 CDN 就再也不换。
- 去掉 `downloadOne()` 里每张图无条件打的一条 `Log.i`（789 张 = 789 次同步 logd 写入，
  12 路并发下 logd 串行成瓶颈）→ 改为 `JmDebug.i`（仅 verbose 下输出）。
