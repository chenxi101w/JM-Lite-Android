搜索接完只走完了 **1/3 的路**。剩下两个大头 —— **详情页** 和 **阅读器图片** —— 接口同样可用且实测通过，

## 一、🥇 P0-1：详情页接 `album` 接口

**现状**：详情走 `PythonBridge.detail()` → Python 抓 HTML → 解析 DOM，慢且字段有限。

**接口实测**（`album?id=<JM号>`，本次已验证）：

```json
{
  "id": 1258292, "name": "...", "author": ["ユウキチ.", ...], "tags": ["青年漫", ...],
  "description": "...(完整简介)", "total_photos": 373, "total_views": "35761", "likes": "7795",
  "series": [{"id":"1258292","name":"","sort":"1"}, ...14 项], "series_id": "1258292",
  "related_list": [12 项], "comment_total": "86"
}
```

**收益**：
1. 详情秒开（省 Python 解释器启动 + HTML 解析）。
2. **拿到真实 `tags`** —— 现在搜索/详情路径都拿不到标签（`jm_bridge` 注释里明说「关键词/作者搜索结果往往不带 tags」，
   只能靠 `enrichTagLibraryFromSearch` 后台补抓 15 本）。接口一次给全 6 个真实标签，
   对**标签库、喜欢画像、推荐算法**是直接的喂料。
3. `series` 直接给出章节列表，不必二次抓取。
4. `related_list` / `total_views` / `likes` 现成可用 → 可做「相关推荐」「按热度排序」。
5. 顺带能拿到 `comments` 数等元数据，UI 可以更丰满。

**成本**：低 —— 复用已有的 `JmApiClient.request()`，加一个 `detail(id)` 方法 + 数据映射。

## 二、🥇 P0-2：阅读图片改直连 CDN（收益最大）

**现状**（`JmRepository.loadImage` → `PythonBridge.imageToFile`）：
```
Kotlin → Python 下载图片 → Pillow 解码 → 落盘 → Coil 读本地文件
```
这正是 **Pillow 缺 WEBP** 那个构建坑的根源。

**接口实测**（`comic_read?id=<photoId>`，本次已验证）：

```json
{
  "scramble_id": 220980, "total_page": 26,
  "images": [
    {"page": 1, "image": "https://cdn-msp3.jmapiproxy1.cc/media/photos/1258292/00001.webp?t=..."},
    ...
  ]
}
```

**直链实测**：`200 image/webp`，**无需 Referer、去掉 `?t=` 参数也可用**。

**收益**：
1. **Coil 直接加载 URL** —— Android 原生 BitmapFactory 从 API 14 起支持 webp 解码（minSdk 24 无压力），
   彻底不需要 Pillow → **「Pillow 缺 WEBP」这个老大难直接蒸发**。
2. 省掉「下载 → 解码 → 落盘 → 再读文件」四跳，翻页/滚动会快一个档次。
3. 图片缓存交给 Coil 统一管理（磁盘缓存已有 256MB 上限），不用自己维护缓存目录与清理逻辑。

**成本**：中 —— 核心是 **scramble 图片还原**。JM 的图是竖向切块后倒序重排的：

- 算法源码已拿到（`utils/Function.js: scramble_image`）：把图竖向切成 `num` 块，倒序重画到 canvas；
- `num = get_num(btoa(aid), btoa(page))`；
- **`aid < scramble_id` 或 GIF 不需要还原**（旧漫未加密）；
- Android 侧用 `Bitmap` + `Canvas.drawBitmap` 等价实现即可。

**风险提示**：还原算法实现错了图片就是「花的」，需要拿几本不同 `scramble_id` 的漫画实测比对。

## 三、🥈 P1-3：补齐搜索参数

目前只有「纯关键词 + 默认排序/时间」走接口（见 `JmRepository.search()` 的判断条件）。待验证参数：

| 参数 | 推测含义 | 现状 |
|---|---|---|
| `o` | 排序（最新/浏览/收藏） | 未验证取值 |
| `y` / `m` | 年 / 月筛选 | 未验证取值 |
| `search_type` | 搜索类型（关键词/作者/标签） | 未验证取值 |

**做法**：拿已知结果集试参数字典（如 `o=mr/mv/mp`），比对返回顺序差异即可确定。
补齐后**所有搜索场景**都能提速，不只是关键词。

## 四、🥈 P1-4：彻底移除 Python（终极形态）

若 P0-1、P0-2 完成，Python 只剩「整本下载」还在用。

**收益**：
- **APK 体积大减**：Python 3.11 运行时 + Pillow + jmcomic 大约 20~30MB；
- **冷启动更快**：不必再后台预热 Python（现在 `JmComicApplication` 有专门的预热 + 门闩逻辑）；
- **构建简化**：去掉 Chaquopy 后，构建期那些坑（buildPython 路径、pip 源、safe-delete 拦截、webp 缺失）全部消失；
- 少一层跨语言调用，全链路可观测。

**成本**：高 —— 需重写下载（OkHttp 拉图 + scramble 还原 + 写盘 + 断点续传/进度/取消），
以及现有 `jm_bridge.py`（1543 行）里所有仍在用的能力。

**建议**：不急于一步到位。先做 P0-1/P0-2，观察「Python 还剩下多少价值」再决定。

## 七、不建议做的事

- **不要照搬它的 Capacitor + React 架构**：它的快来自服务端 JSON API，与 React 无关；
  而 WebView 渲染流畅度低于现有原生 Compose，改过去是负优化。
- **不要接它的广告/会员/金币/论坛模块**：那是它的商业体系，与「本地漫画阅读器」定位无关。
- **不要盲目全量依赖它的接口**：第三方服务，域名会轮换（故有线路配置源）、协议可能变更。
  现有「接口优先 + Python 回退」的双通道设计应保持，不要拆掉回退分支。
