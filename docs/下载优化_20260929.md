# JM 轻量版下载链路优化评估

**日期**：2026-09-29
**结论来源**：本机实测（网络基准 + CPU 解码基准），非推测

---

## 零、一句话结论

下载慢的锅**不全是网络**：现有解码链路每张图有 **75% 的 CPU 是纯粹的绕道浪费**
（webp → PNG → PIL → JPEG 三次编解码 + 两次跨语言搬运）。
网络侧 CDN 限速约 1.2MB/s 是另一头瓶颈。两者叠加后，一本 14 章漫画要 2~4 分钟。

---

## 一、实测数据

### 1) 网络侧（本机直连，26 张图 / 16.1MB / 单张 120KB webp）

| 并发 | 耗时 | 速度 |
|---|---|---|
| 4 | 23.83 s | 0.68 MB/s |
| **12（当前默认）** | **15.94 s** | **1.01 MB/s** |
| 16 | 13.76 s | 1.17 MB/s |

- 并发从 4 提到 16 只快了 1.7 倍（而非 4 倍）→ **服务端有总量限速**，不是客户端带宽问题。
- 但**提高并发仍有收益**：12 → 16 约 +14%。

### 2) CPU 侧（单张 702×1000，本机 R7-5700U）

| 步骤 | 耗时 | 评价 |
|---|---|---|
| webp 解码 | 24.6 ms | 必要 |
| **PNG 编码** | **80.6 ms** | ❌ 纯浪费 |
| **PNG 解码** | **14.2 ms** | ❌ 纯浪费 |
| JPEG 编码 | 6.3 ms | 必要 |
| 合计 | **125.6 ms/张** | **浪费占 75%** |

> 手机 CPU 弱于本机 2~3 倍，且下面还有未计入的开销，实际更糟。

---

## 二、根因：为什么会有 PNG 绕道

`jm_bridge._patch_jm_image_tool_open_image()` 的注释写得很清楚：

> jmcomic 的 `JmImageTool.open_image` 用 `PIL.Image.open`；**Chaquopy Pillow 缺 WEBP 解码器**。
> 对 WEBP 改用 Android BitmapFactory 解码为 **PNG** 后再交给 PIL，后续 descramble / save 不变。

于是每张图的实际链路是：

```
Python 下载 webp bytes
  → 跨语言调 Java BitmapFactory 解码 webp
  → Java 编码成 PNG bytes            ← 80.6ms 浪费
  → PNG bytes 跨语言搬回 Python      ← 未计入的复制/搬运开销
  → PIL 解码 PNG                     ← 14.2ms 浪费
  → PIL 做 scramble 像素重排
  → PIL 编码 JPEG
  → 写盘
```

**三次编解码 + 两次跨语言搬运**，其中两次编解码纯粹是因为「Pillow 缺 webp」而绕的道。

更糟的是：**Python GIL** 让解码（CPU 密集）无法真正并行 ——
12 个线程同时下载，但解码基本串行化，所以并发调再高也救不了 CPU 这一段。

## 三、优化方案

### 🥇 方案 A（推荐）：下载零解码 —— 存原始 webp

| 项 | 内容 |
|---|---|
| 改动 | Python 侧 `download_by_image_detail(decode_image=False)`，文件存 `.webp`（**基本 1 行改动**）；阅读时由 Kotlin 解码 + 还原 scramble |
| 收益 | ① 下载时间 ≈ **纯网络时间**（去掉全部 CPU）；② 存储省 50%+（webp 120KB vs 还原后 JPEG 通常 250~400KB）；③ 不再受 GIL 拖累 |
| 成本 | Kotlin 侧实现 scramble 还原 + Coil 自定义转换器（**这也是方案 B 的前置**） |
| 备注 | 需兼容历史数据（已下载的 `.jpg` 是还原过的，直接用；`.webp` 才需还原）—— 阅读器的 `loadLocalPaths` 已同时接受两种扩展名 |

### 🥈 方案 B（渐进）：原生一次完成，不绕 PNG

| 项 | 内容 |
|---|---|
| 改动 | 解码搬到 Kotlin：`BitmapFactory` 解码 webp → `Canvas` 重排 scramble → `Bitmap.compress` 存 JPEG/WebP，全程不经 PIL |
| 收益 | 省掉 75% 的 CPU 浪费（约 95ms/张），且原生解码**可真并行**，不受 GIL 限制 |
| 成本 | 同样需要实现 scramble 还原；数据流形态不变（仍是还原后的图落盘） |
| 适合 | 想保持"下载即得到可读图片"的现有语义时 |

### 🥉 方案 C（最小改动）

- 把并发默认 **12 提到 16**（配置项 `max_concurrent_downloads` 已支持 1~16），约 +14%。
- 把 PNG 中转换成 **PNG 压缩级别 1**（`Image.save(..., compress_level=1)`）—— PNG 默认压缩级别 6 是最慢的部分。
  预计能把 80.6ms 降到 20~30ms，代价是 PNG 体积变大（但只作中转，不落盘）。
- 收益有限，但**改动只有一行**，可作为短期止血。

### 🥉 方案 D（终极）：下载彻底去掉 Python

- OkHttp 并发直下 CDN + 原生解码还原，完全不走 Chaquopy。
- 与方案 A 组合 = 下载链路全 Kotlin：**零跨语言、零 GIL、零 Chaquopy 开销**。
- 同时 APK 体积可省 20~30MB（若 Python 不再被任何功能需要）。

---

## 四、预期收益（一本 14 章 × 26 张 = 364 张）

| 项 | 现状 | 方案 A + C | 说明 |
|---|---|---|---|
| 网络 | ~37 s | ~32 s | 44MB @ 1.2MB/s；并发提到 16 |
| CPU 解码 | ~45 s（PC）/ **90~150 s（手机）** | **≈ 0** | 方案 A 完全不做解码 |
| 合计 | **~2~4 分钟** | **~30~40 秒** | 网络成为唯一瓶颈 |

> 阅读时还原的成本：按需解码当前页（原生 <30ms/张），且滚动时只处理可视区，
> 体感远优于"下载阶段串行死等"。

---

## 五、共同前置：scramble 还原必须先在 Kotlin 落地

方案 A / B / D 都依赖同一个能力 —— **图片切割还原**：

- 规则：`aid < scramble_id` 或 GIF **不需要还原**；否则图片被竖向切成 `num` 块倒序重排；
- `num = get_num(btoa(aid), btoa(page))`；
- 算法原型见同源客户端 `utils/Function.js: scramble_image`（切块 + 倒序 + `drawImage`）；
- Android 侧用 `Bitmap` + `Canvas.drawBitmap` 等价实现。

**建议：先做这个还原能力（用已知的可视样本验证正确性），再选方案 A 或 B 接入。**

---

## 六、建议推进顺序

1. **方案 C 止血**（并发 16 + PNG compress_level=1）—— 一行级改动，立刻可见
2. **实现 scramble 还原**（Kotlin/Canvas）—— 用「aid > scramble_id 的漫画」验证
3. **上方案 A**（存原始 webp + 阅读时还原）—— 下载提速到网络极限、存储省一半
4. 评估**方案 D**（彻底去 Python）
